# LINE AI Chat 成本報告

**日期**：2026-09-25 ｜ **範圍**：LINE 官方帳號 AI Chat 五層架構的 AI 分層成本與 TCO
**基底**：AWS Amplify SSR + DynamoDB（只計 AI 分層與向量搜尋的增量成本）
**配套**：完整架構見 [`line-ai-chat-architecture-and-tco-2026-09-25.md`](./line-ai-chat-architecture-and-tco-2026-09-25.md)；可調試算表 [`line-ai-chat-cost-model.xlsx`](./line-ai-chat-cost-model.xlsx)

---

## 一、結論（TL;DR）

1. **現況每月 < 1,000 則訊息 = AI 成本每月不到 US$0.5**（NT$14 上下）。此流量下任何自建 GPU 或 RunPod 方案都是浪費。
2. **每則混合成本 431 µ$ ≈ NT$0.0138**。其中 LLM 佔約 96%，而**只佔 5% 流量的 L5（高階模型/真人）就吃掉 62% 的成本**。
3. **降成本最大的槓桿是壓低 L5 命中率**（把複雜問題盡量在 L1–L4 解決），效果遠大於在 L4 換更便宜的模型。
4. **純雲 Pay-as-you-go（方案 A）在所有可預見流量都是最便宜**。自建 GPU 要每月約 250 萬則、RunPod 常駐 worker 要約 186 萬則才追平純雲——是現況的 2,000 倍以上。
5. **建議**：留在方案 A，直到月訊息量 > 50 萬則或 AI 月費連三個月 > US$200 再重新評估。本機/RunPod 保留為可插拔選項，不提前投資。

---

## 二、假設與計價基礎

- 匯率 FX = 32 NT$/US$；成本以 micro-USD（µ$，1 USD = 1,000,000 µ$）計，對齊系統帳本 `ai-usage-ledger`。
- 分層命中率（可調）：L1 30% / L2 25% / L3 20% / L4 20% / L5 5%。
- 累積成本概念：一則走到 L5 的訊息，已先付了 L1+L2+L3+L4，因此用 `blended = Σ 命中率 × 累積成本` 衡量，而非單看某層。
- L4 主模型 Gemini 3.1 Flash-Lite（$0.25/$1.50 每 M）；L5 Claude Haiku 4.5（$1.00/$5.00 每 M）；embedding text-embedding-3-small（$0.02/M）。
- 每則 token 假設：L4 輸入 1,960 / 輸出 180；L5 輸入 2,760 / 輸出 350；embedding 60。
- AWS 增量（DynamoDB on-demand、Lambda 計費模型）免費額度視為已被平台其他流量用掉（保守）。

## 三、每則訊息成本拆解

| 層 | 該層新增 inc (µ$) | 累積 cum (µ$) | 命中率 | 貢獻 (µ$) |
|---|---:|---:|---:|---:|
| L1 Postback / 圖文選單 | 2.8 | 2.8 | 30% | 0.8 |
| L2 Keyword / Regex 規則 | 0 | 2.8 | 25% | 0.7 |
| L3 Semantic FAQ 向量 | 8.0 | 10.8 | 20% | 2.2 |
| L4 便宜 LLM（RAG） | 787.5 | 798.3 | 20% | 159.7 |
| L5 高階 / 真人轉接 | 4,562.5 | 5,360.8 | 5% | 268.1 |
| **混合（blended）** | | | **100%** | **431.4** |

**每則 431.4 µ$ ≈ NT$0.0138。** 三個要看懂的重點：

- **LLM 佔 blended ≈ 96%**（L4+L5 的 token 費 415.5 µ$）。L1–L3 合計不到 12 µ$，幾乎免費。
- **L5 佔 62%**：只佔 5% 流量卻是最大成本來源。
- 分層的價值**不是**省 L1–L3 的錢，而是**把 L4/L5 的比例壓下來**。

## 五、三方案比較（A 純雲 / B RunPod / C 自建 GPU）

B 與 C 只把 **L4 LLM** 搬離雲端，L1–L3 與 L5 仍在雲端。誠實的總成本 = 雲端 A 總成本 − 雲端 L4 LLM 費 + 替代成本。

| 月訊息量 | A 純雲 US$ | B RunPod US$ | C 自建 GPU US$ | 最便宜 |
|---|---:|---:|---:|:--:|
| 1,000 | 0.43 | 1.80 | 441.2 | **A** |
| 10,000 | 4.31 | 17.92 | 443.5 | **A** |
| 100,000 | 43.14 | 173.10 | 466.3 | **A** |
| 1,000,000 | 431.42 | 594.01 | 694.2 | **A** |

**方案 B（RunPod Serverless）**：理論下限（100% 溫機）也只比雲端便宜 37%，一旦有冷啟（25 秒）就被推到 5–8 倍貴。隱藏成本：冷啟期間使用者無回應、模型鏡像儲存、無 SLA。**只有在 L4 被迫升到 mini/Haiku 級模型時才有機會贏。**

**方案 C（自建 RTX 5090）固定成本 = NT$14,110/月 ≈ US$441**：

| 項目 | NT$/月 |
|---|---:|
| 設備折舊（NT$245k / 36 月） | 6,806 |
| 待機電費（90W × 730h × 4.5） | 296 |
| **維護工時（4h × 1,200）** | **4,800** |
| UPS / 備援折舊 | 167 |
| 故障 / 升級準備金（10%/年） | 2,042 |
| **合計** | **14,110** |

維護工時佔 34%，是最大單項。單機無 HA，故障期間 L4 全部要 fallback 到雲端；家用電/網路中斷不在 UPS 涵蓋；折舊期內 GPU 跌價不退錢。

## 七、敏感度（哪些變數會翻盤）

| 變數 | 變動 | 影響 |
|---|---|---|
| **L5 命中率** | 5% → 10% | blended 431 → 660 µ$（+53%），最大槓桿 |
| **L4 模型等級** | Flash-Lite → mini / Haiku | blended 升到 811 / 956 µ$；C 勝 A 門檻降到 79 萬 / 63 萬則 |
| 命中率分布 | 樂觀（規則層強）vs 悲觀（規則層弱） | blended 175 µ$ vs 1,394 µ$，差 8 倍 |
| L4 tokens/則 | ×2（RAG/歷史加長） | C 勝 A 門檻減半 |
| 維護工時 | 4h → 0h（自欺情境） | C 勝 A 降到 ~163 萬則 |
| 電價 | 4.5 → 9.39 NT$/度 | C 幾乎不動（< 3%） |
| L5 prompt cache | 命中 50% | blended −14% |

**啟示**：把訊息趕進 L1/L2（規則層）的價值，遠大於在 L4/L5 換模型。命中率分布從悲觀到樂觀，成本差 8 倍。

---

## 八、決策門檻

1. **留在方案 A（純雲）**：直到月訊息量 > 50 萬則，或 AI 月費連續 3 個月 > US$200。
2. **重評方案 B（RunPod 常駐 worker）**：當 L4+L5 請求 > 5,000/日（≈15 萬/月）且雲端 L4 單價 ≥ US$0.002/req，或需要 API 沒有的模型。RunPod flex 只當「零 CAPEX 試跑本地模型品質」的實驗。
3. **考慮方案 C（自建 GPU）**：需三條件同時成立——單卡持續利用率 > 30%（≈130 萬則/月）、雲端 fallback 已演練、有人承擔每月維護工時。
4. **合規例外**：資料落地/隱私法遵可直接跳 C，但這是合規成本，不是省錢。
5. **治理護欄**：預算 GLOBAL 月上限先設 US$50、日上限 US$5；帳本以 `line-l3/l4/l5` 分開記，三個月後用真實用量回填命中率、重算本報告。
